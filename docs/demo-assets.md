# Demo assets

The README's screenshots and the demo GIF are **real captures** of the running app, and one command regenerates them, so they never drift from the product.

```bash
pnpm screenshots          # start a fresh seeded API and a production build, capture every page, stop
pnpm screenshots --gif    # ... and also record docs/assets/demo.gif
```

## What it writes

| File                                                    | Used by      | What it shows                                                                                                                |
| ------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `docs/assets/dashboard.png`                             | README       | The dashboard with the live event stream and detection test coverage.                                                        |
| `docs/assets/detection-playground.png`                  | README       | A Sigma rule, a dataset and the match trace.                                                                                 |
| `docs/assets/story-mode.png`                            | README       | The developer-workstation story part-way through, with the investigation graph.                                              |
| `docs/assets/mitre-coverage.png`                        | README       | The ATT&CK coverage heatmap with platform filters.                                                                           |
| `docs/assets/demo.gif`                                  | README       | The 80-second demo, at 2-second steps, looping.                                                                              |
| `docs/assets/screenshots/<name>-dark.png`, `-light.png` | README, docs | Every page above plus alerts, labs, lifecycle, AI security, demo, rule quality and the investigation report, in both themes. |

The four `.png` files at the top level are copies of the dark captures. Nothing is composited, annotated or generated by a model.

## Options

```bash
pnpm screenshots --url http://localhost:3000            # reuse an instance that is already running
pnpm screenshots --only=dashboard,story-mode            # only some shots (see the list in scripts/screenshots.mjs)
pnpm screenshots --gif-only --gif-step=1                # only the GIF, one frame per demo second (larger file)
THEMES=dark pnpm screenshots                            # one theme
PW_CHANNEL=msedge pnpm screenshots                      # use an installed browser instead of downloading Chromium
SHOTS_API_PORT=8300 SHOTS_WEB_PORT=3300 pnpm screenshots
```

Without `--url` the script starts its own API (a throw-away SQLite database, demo data seeded) and web app, so the result does not depend on anything you were doing. Building the web app takes a minute or two; set `E2E_REUSE_BUILD=1` to reuse an existing build while iterating.

## How the GIF is made

There is no screen recorder and no video tooling. The demo is a pure function of time ([Demo mode](demo-mode.md)), so the script loads `/demo?t=0`, `/demo?t=2`, `/demo?t=4` ... and screenshots each moment. The frames are encoded with [`gifenc`](https://github.com/mattdesl/gifenc) into a looping GIF in which unchanged pixels are transparent, which keeps it well under a megabyte. That makes it reproducible: the same commit always produces the same frames.

Animations and transitions are switched off during capture, so an image never catches something half-way between two states.

## Before committing new images

- Look at them. A capture that shows an error page or an empty panel is a bug in the script or the app, not something to commit.
- Keep the GIF under about 2 MB (raise `--gif-step`, or lower the viewport in `scripts/screenshots.mjs`).
- Regenerate all of them together so the README does not mix versions of the UI.

## Recording a video for a talk or a post

For a live recording, open `/demo?autoplay=1&speed=1` in a browser window sized to your slide, and use your operating system's recorder. The demo's timing is fixed, so a second take looks the same as the first. `/demo?t=52` opens the demo paused at a good still frame.
